\section{Q4 --- Campaign Analysis}
%==============================================================================

The white-box campaign ran for 75,277 seconds and executed 62,454,465 test cases
at 829.65 exec/s. Final AFL++ status metrics were: corpus count 1,103,
stability 100.00\%, bitmap coverage 31.69\% (974 of 3,074 edges), cycles done 323,
and 0 crashes / 0 hangs.

The edge-discovery curve in \texttt{plot\_output/edges.png} shows a three-phase shape:
an aggressive early discovery phase, a long diminishing-returns middle phase, and a final plateau.
From \texttt{findings/default/plot\_data}, coverage milestones were:
\begin{itemize}
  \item 689 edges (22.41\%) at 61 s --- early rapid discovery
  \item 783 edges (25.47\%) at 530 s --- acceleration phase
  \item 935 edges (30.42\%) at 7,183 s --- approaching saturation
  \item 959 edges (31.20\%) at 28,461 s --- diminishing returns
  \item 973 edges (31.69\%) at 49,478 s --- final new edge
  \item 974 edges (31.69\%) at 54,735 s --- plateau reached
\end{itemize}

This timestamped progression supports a saturation argument. After roughly 15.2 hours,
the campaign stopped finding new edges altogether, while the corpus still grew from 1,063
inputs at 54,735 s to 1,103 inputs at the end of the run. In other words, later mutations
mostly produced new inputs that exercised already-known paths rather than discovering new
control-flow. The campaign therefore reached practical saturation for this harness/library pair.

\section{Q5 --- Crash Triage}
%==============================================================================

Our white-box campaign found no real crashes after 62.4M executions. This is acceptable and defensible for libpng 1.2.56: it is a heavily analyzed target, and the CRC patch plus harness guards significantly reduced false positives and OOM-style noise.

We validated our setup by doing a synthetic bug injection.
A single heap-buffer-overflow was added inside `png_read_row()` immediately after the library copies the decompressed row into `prev_row`. In the container, this is applied only to a separate copy of the library (`libpng-1.2.56_bugged`), while the original `libpng-1.2.56` remains untouched for the normal campaign. The injected code writes past the `prev_row` allocation, producing a deterministic out-of-bounds write that AddressSanitizer (ASan) catches when the harness is compiled with `-fsanitize=address`.

Why this location: `png_read_row()` is on the normal input-processing path and
is exercised by the existing harness loop.

Reproduction steps (exact commands):
\begin{lstlisting}
# From host: start container with repo mounted
docker run --rm -it -v "$PWD":/work -w /work cs412-fuzz-env bash

# Inside container: build instrumented libpng + harness against bugged copy
make build LIB_DIR=libpng-1.2.56_bugged

# Quick single-run test (ASan should abort and print heap-buffer-overflow)
./harness_whitebox seeds/basn2c16.png

# 60s AFL++ validation fuzz (should find and save crashes)
timeout 60s afl-fuzz -i seeds/ -o findings_synth -x dictionaries/png.dict -- ./harness_whitebox @@

# Inspect found crashes
ls -la findings_synth/default/crashes/ | head -20
\end{lstlisting}

Revert the synthetic bug (safe):
\begin{lstlisting}
# Rebuild the normal, untouched baseline library
make build LIB_DIR=libpng-1.2.56
\end{lstlisting}

This synthetic bug demonstration proves that (1) our build pipeline includes AddressSanitizer, (2) ASan is active at runtime and detects memory errors, and (3) AFL++ can fuzz instrumented binaries without issues. Since the 62.4M-execution white-box campaign produced no crashes despite reaching 31.69\% coverage, the most reasonable conclusion is that libpng 1.2.56 does not contain an easily reachable memory-corruption bug under our harness configuration.
