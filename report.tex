% --- ABSTRACT ---
\begin{abstract}
This report details a coverage-guided fuzzing campaign against libpng 1.2.56 using AFL++. We evaluate the library's security through both instrumented (white-box) and QEMU-mode (black-box) fuzzing. Our results quantify the performance impact of AddressSanitizer (ASan) and persistent mode, while investigating the code coverage achieved through mutation-based analysis.
\end{abstract}

\section{Q1: Harness Design}

\subsection{Entry Point Justification}
We target the \texttt{libpng 1.2.56} sequential decoder via the low-level API:
\texttt{png\_read\_info()}, \texttt{png\_set\_expand()},
\texttt{png\_read\_update\_info()}, and \texttt{png\_read\_row()}.
The decoder is the highest-value target: it processes fully untrusted input
through CRC validation, zlib decompression, and pixel transformation, all of
which have been sources of historical CVEs. Calling \texttt{png\_set\_expand()}
explicitly forces the fuzzer into colour-transformation paths (palette-to-RGB,
greyscale expansion) where CVE-2015-8126 originated.

\textbf{Alternatives rejected:}
\begin{itemize}[leftmargin=*]
    \item \textbf{Encoder:} processes application-supplied, already-validated data;
    far less likely to contain memory-safety bugs triggered by malformed input.
    \item \textbf{High-level API (\texttt{png\_read\_png}):} allocates full image
    buffers based on header dimensions, making the fuzzer trivially OOM-crashable
    on ``zip bomb'' headers without reaching real parsing logic.
\end{itemize}

\subsection{Data Flow and Guard Rationale}
AFL++ delivers a mutated file path via \texttt{argv[1]}; \texttt{fopen} opens it
and \texttt{png\_init\_io()} binds it to the \texttt{png\_struct}, after which all
subsequent library calls read from that source.

\textbf{Guards and their fuzzing rationale:}
\begin{itemize}[leftmargin=*]
    \item \textbf{\texttt{setjmp(png\_jmpbuf(png))}}: libpng signals errors via
    \texttt{longjmp}. Without this handler every malformed chunk causes an
    unhandled jump that AFL++ records as a crash, flooding results with false
    positives.
    \item \textbf{Dimension limit (\texttt{height * rowbytes < 10\,MB})}: prevents
    OOM on crafted headers with gargantuan dimensions, keeping execution speed high.
    \item \textbf{\texttt{png\_read\_end()}}: reads post-IDAT ancillary chunks
    (\texttt{tEXt}, \texttt{zTXt}, \texttt{iTXt}), exposing the text-chunk parsing
    code that contains CVE-2016-10087 (\texttt{png\_set\_text\_2}).
    \item \textbf{Strict cleanup (\texttt{png\_destroy\_read\_struct})}: frees all
    library state between iterations, preventing memory accumulation that would
    eventually crash the fuzzer for reasons unrelated to the library's logic.
\end{itemize}

\section{Q2: Instrumentation and Sanitizers}

\subsection{Compiler Flags and Instrumentation}
We used the following flags during the white-box build phase:

\begin{itemize}
    \item \texttt{CC=afl-clang-fast}: This selects the AFL++ LLVM-based compiler
    wrapper. It performs IR-level instrumentation by injecting coverage callbacks
    at every branch during compilation. This allows AFL++ to track edge coverage
    in a 64KB shared memory bitmap.
    \item \texttt{-fsanitize=address}: Enables AddressSanitizer (ASan). ASan uses
    ``shadow memory'' (mapping 8 bytes of application memory to 1 byte of shadow
    memory) to track memory state. It places ``redzones'' around stack and heap
    objects to detect out-of-bounds accesses immediately.
    \item \texttt{-g}: Includes debug symbols. While not strictly necessary for
    fuzzing, it is vital for triage (Q5) to map crash addresses back to source
    code lines.
    \item \texttt{-O1}: We chose moderate optimization. High optimization
    (\texttt{-O3}) can sometimes inline vulnerable code or optimize away
    ``useless'' memory accesses that ASan needs to monitor.
\end{itemize}

\subsection{Library Patches: CRC Removal}
We applied the \texttt{libpng-nocrc.patch} provided in the AFL++ utilities. This
patch modifies \texttt{png\_crc\_finish()} to return 0 (success) unconditionally.

\textbf{Impact on Path Discovery:} This is the most critical modification for
\texttt{libpng}. Every PNG chunk contains a 4-byte CRC-32 checksum. When AFL++
mutates the chunk data (the ``Havoc'' stage), the checksum becomes invalid.
Without this patch, the library calls \texttt{png\_error()} and terminates
immediately upon seeing an invalid CRC.

If omitted, the fuzzer would be trapped at the library's ``front door.'' It would
find thousands of inputs that trigger the same CRC error path but would never
reach the deeper, vulnerable logic (decompression, palette handling, or pixel
transformations). The patch essentially disables the data integrity gatekeeper,
allowing mutated inputs to reach the complex attack surface.

\subsection{Impact of ASan Omission}
If \texttt{ASan} were omitted, the fuzzer would only detect crashes that cause a
\texttt{SIGSEGV} (e.g., jumping to invalid memory). Subtle bugs like a 1-byte
heap-buffer-overflow or an out-of-bounds read that does not hit unmapped memory
would go completely unnoticed, resulting in a false sense of security.



\section{Q3: Seed Corpus and Dictionary}

\subsection{Seed Corpus}
We used 9 small, valid PNGs from \texttt{libpng-1.2.56/contrib/pngsuite/},
chosen for structural diversity: greyscale (4-bit, 16-bit), truecolour RGB
(8-bit, 16-bit), RGBA, indexed palette with \texttt{tRNS}, palette with
\texttt{gAMA}, and two interlaced images (\texttt{s01i3p01}, \texttt{s40i3p04}).
Each seed exercises a distinct code path through \texttt{png\_read\_info()} and
the \texttt{png\_set\_expand()} transformation pipeline; interlaced seeds seed
the Adam7 logic that pure mutation rarely reaches. Keeping seeds small (under
10\,KB) avoids slow calibration and lets AFL++ grow the corpus organically.

\subsection{Dictionary}
We used the standard AFL++ PNG dictionary (\texttt{png.dict}, 27 entries).
In formal grammar terms, the entries are \textbf{terminal symbols} of the PNG
chunk language: the 8-byte magic header \texttt{\textbackslash x89PNG\ldots}
(the start symbol) and 26 four-byte chunk-type identifiers
(\texttt{IHDR}, \texttt{IDAT}, \texttt{IEND}, \texttt{PLTE},
\texttt{iTXt}, \texttt{zTXt}, \texttt{tRNS}, \texttt{iCCP}, \ldots).
Without the dictionary, discovering the token \texttt{IHDR} by random bit flips
has a $1/2^{32}$ probability per byte position; the dictionary lets AFL++ splice
these terminals directly into mutations, dramatically accelerating discovery of
chunk-dispatch code paths.

\subsection{Strategy Contribution (from AFL++ status screen)}

\begin{center}
\small
\begin{tabular}{lrr}
\toprule
Strategy & New finds & Executions \\
\midrule
Bit/byte flips \& arithmetics & 21  & $\sim$1.1M \\

\end{center}

Havoc found \textbf{840 of 863 new corpus entries (97.3\%)} by applying
random combinations of mutations across 61M executions. The dictionary
contributed 1 new find, consistent with its role as an early-campaign
accelerator: once chunk-type paths are seeded into the corpus, havoc-based
mutation of valid inputs dominates coverage growth.

\section{Q4: Campaign Analysis}
The white-box campaign ran for 75,277 seconds and executed 62,454,465 test cases
at 829.65 exec/s. Final AFL++ status metrics were: corpus count 1,103,
stability 100.00\%, bitmap coverage 31.69\% (974 of 3,074 edges), cycles done 323,
and 0 crashes / 0 hangs.

The edge-discovery curve in \texttt{plot\_output/edges.png} shows a three-phase shape:
an aggressive early discovery phase, a long diminishing-returns middle phase, and a final plateau.
From \texttt{findings/default/plot\_data}, coverage milestones were:
\begin{itemize}
  \item 689 edges (22.41\%) at 61 s --- early rapid discovery
  \item 783 edges (25.47\%) at 530 s --- acceleration phase
  \item 935 edges (30.42\%) at 7,183 s --- approaching saturation
  \item 959 edges (31.20\%) at 28,461 s --- diminishing returns
  \item 973 edges (31.69\%) at 49,478 s --- final new edge
  \item 974 edges (31.69\%) at 54,735 s --- plateau reached
\end{itemize}

This timestamped progression supports a saturation argument. After roughly 15.2 hours,
the campaign stopped finding new edges altogether, while the corpus still grew from 1,063
inputs at 54,735 s to 1,103 inputs at the end of the run. In other words, later mutations
mostly produced new inputs that exercised already-known paths rather than discovering new
control-flow. The campaign therefore reached practical saturation for this harness/library pair.

\section{Q5: Crash Triage}
%=====================================================================

Our white-box campaign found no real crashes after 62.4M executions. This is
acceptable and defensible for \texttt{libpng 1.2.56}: it is a heavily analyzed
target, and the CRC patch plus harness guards significantly reduced false
positives and OOM-style noise.

We validated our setup by injecting a synthetic bug. A single heap-buffer-overflow
was added inside \texttt{png\_read\_row()} immediately after the library copies the
decompressed row into \texttt{prev\_row}. This is applied only to a separate copy
of the library (\texttt{libpng-1.2.56\_bugged}), while the original
\texttt{libpng-1.2.56} remains untouched for the normal campaign. The injected
code writes past the \texttt{prev\_row} allocation, producing a deterministic
out-of-bounds write that ASan catches when the harness is compiled with
\texttt{-fsanitize=address}.

Why this location: \texttt{png\_read\_row()} is on the normal input-processing
path and is exercised by the existing harness loop.

Reproduction steps are listed in Sub-Appendix C\@.

AFL++ found 10 crashes within 85 seconds. The minimized input was reduced from
357 to 325 bytes by \texttt{afl-tmin}. The resulting ASan stack trace (see
Figure~\ref{fig:status_bugged} and Sub-Appendix C) confirms a heap-buffer-overflow WRITE of 1 byte at
\texttt{pngread.c:789}, 4 bytes before an 885-byte \texttt{row\_ptr} allocation.

This synthetic bug demonstration proves that (1) our build pipeline includes
AddressSanitizer, (2) ASan is active at runtime and detects memory errors, and
(3) AFL++ can find crashes in instrumented binaries within minutes.

\textbf{Why no real bugs were found:} Three factors explain the absence of crashes
in the main campaign. First, \texttt{libpng 1.2.56} is a mature, extensively
audited library --- CVE-2015-8126 was already patched in 1.2.54 (before our
target), and while CVE-2016-10087 technically affects 1.2.56, it is a
NULL-pointer dereference triggered by a specific \texttt{png\_set\_text}
code path that our harness never exercises, leaving few low-hanging
memory-safety bugs reachable by our mutation-based campaign. Second, our
campaign reached only 31.69\% edge coverage (974 of 3,074 edges): the remaining
68\% of code paths --- including Adam7 interlacing, 16-bit depth processing, and
compressed ancillary chunks --- were never exercised, so bugs in those paths could
not be found. Third, mutation-based fuzzing without structure-aware generation
struggles to produce the precise byte sequences needed to pass zlib decompression
and reach the deep pixel-transformation logic where historical bugs have lived.
The synthetic bug validation confirms our instrumentation and ASan are working
correctly: the absence of crashes is a genuine result, not a setup failure.


\section{Q6: Attack Surface Analysis}

\subsection{Applications and Attack Scenarios}
\texttt{libpng} is critical for cross-platform image rendering. We identify two primary attack vectors:
\begin{itemize}[leftmargin=*]
    \item \textbf{Mozilla Firefox (Web Rendering):} Browsers automatically parse PNGs from untrusted web servers. A malicious PNG triggering a buffer overflow (e.g., CVE-2015-8126) allows \textbf{code execution within the renderer process}, which an attacker could chain with a sandbox escape to achieve full Remote Code Execution (RCE).
    \item \textbf{ImageMagick (Server-side Processing):} Web backends use this to process user uploads. A malformed chunk triggering a NULL-pointer dereference (CVE-2016-10087) causes a \textbf{Denial of Service (DoS)} or memory disclosure, crashing the thumbnail generation service.
\end{itemize}

\subsection{Coverage Gaps and Security Implications}
Our harness focuses on linear decoding, leaving several critical paths unexercised:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Encoding API (\texttt{png\_write\_*}):} Functions in \texttt{pngwrite.c} and \texttt{pngwtran.c} are never called. Although encoders typically handle trusted data, vulnerabilities can arise during raw-to-chunk conversion if metadata checks are inconsistent.
    \item \textbf{Adam7 Interlacing (\texttt{png\_do\_read\_interlace}):} Our harness reads rows linearly and does not invoke interlacing logic in \texttt{pngrutil.c}. Interlacing involves complex, non-linear coordinate math that is historically prone to \textbf{off-by-one errors} and heap corruption when calculating buffer offsets for incomplete passes.
\end{enumerate}
An attacker targeting Firefox's image rendering pipeline or ImageMagick's upload processing could exploit either gap without our campaign detecting it.


\section{Q7: Binary-Only Fuzzing with QEMU Mode}

\subsection{Comparative Analysis}
We executed a parallel campaign using AFL++ QEMU mode (\texttt{-Q}) against an
uninstrumented \texttt{libpng} binary compiled with standard \texttt{gcc} and no
sanitizers. The results after $\sim$35 minutes (Figure~\ref{fig:status_comparison})
are summarized in Table~\ref{tab:qemu_comparison}:

\begin{table}[h]
\centering
\small
\begin{tabular}{l l l}
\hline
\textbf{Metric} & \textbf{Instrumented} & \textbf{QEMU Mode (-Q)} \\ \hline
Exec Speed      & 861.8 exec/s          & 2,384 exec/s            \\
Map Density     & 8.65\%                & 0.74\%                  \\
Corpus Count    & 614 items             & 872 items               \\ \hline
\end{tabular}
\caption{Comparison metrics after 35 minutes of fuzzing.}
\label{tab:qemu_comparison}
\end{table}

\subsection{Analysis and Differences}
\begin{itemize}[leftmargin=*]
    \item \textbf{Execution Speed:} QEMU mode achieved 2,384 exec/s vs.\ 861.8 exec/s
    for the instrumented build. The instrumented build is slowed by
    \textbf{AddressSanitizer (ASan)}, which inserts a shadow-memory check before
    every memory access. Without ASan, native compile-time instrumentation is
    typically 10--50$\times$ faster than QEMU emulation; here ASan inverts the
    relationship.
    \item \textbf{Map Density (Coverage):} The instrumented campaign reached
    8.65\% edge coverage vs.\ only 0.74\% for QEMU. Compile-time instrumentation
    captures every branch transition at the IR level, whereas QEMU's block-level
    translation logs coarser basic-block transitions and frequently collapses
    multiple branches into a single translated block.
    \item \textbf{Corpus Count:} QEMU produced a larger corpus (872 vs.\ 614
    items) despite lower coverage. Without precise edge feedback, AFL++ accepts
    test cases that do not exercise genuinely new control-flow, resulting in a
    larger but more redundant corpus.
\end{itemize}

\subsection{Coverage Collection Mechanism}
\textbf{Compile-Time Instrumentation} (\texttt{afl-clang-fast}) statically injects
coverage checkpoints at every branch during compilation, adding only a few
instructions per edge with no translation overhead at runtime.

\textbf{QEMU Mode} uses \textbf{Dynamic Binary Translation} via the Tiny Code
Generator (TCG): guest instruction blocks are translated to host code at runtime,
and AFL++ hooks the TCG pipeline to log basic-block transitions. This emulation
layer adds substantial per-block overhead and produces coarser coverage maps,
explaining the 11.7$\times$ lower map density despite a higher raw execution rate.

\section{Q8: Instrumentation Depth \& Performance}

\subsection{Instrumented Edge Counts}
At startup, \texttt{afl-fuzz} reports the total number of instrumented edges in
the harness binary via \texttt{fuzzer\_stats}. For our final \texttt{harness\_whitebox}
binary, the total is \textbf{3,074 edges}. This count covers both the libpng
1.2.56 library code and the small \texttt{main()} function in our harness
(\texttt{src/harness.c}). The harness \texttt{main()} contributes at most
$\sim$10 edges (argument check, \texttt{fopen}, \texttt{setjmp} branch, four
API calls, cleanup), so the \textbf{library-alone edge count is approximately
3,064} --- less than 0.4\% difference from the binary total. The overwhelming
majority of edges originate from libpng's parsing, decompression, and
transformation pipeline, not from our harness wrapper.

After 75,277 seconds of fuzzing, the campaign reached \textbf{974 edges
(31.69\% map density)}. The remaining 2,100 edges (68.31\%) were never
triggered. Many code paths in libpng require very specific input conditions to
activate, such as Adam7 interlacing (\texttt{png\_do\_read\_interlace} in
\texttt{pngrutil.c}), 16-bit depth processing, palette-mode expansion, or rare
ancillary chunks (\texttt{zTXt}, \texttt{iTXt}). Mutation-based fuzzing without
structure-aware generation struggles to produce the precise byte sequences needed
to unlock these paths, causing the campaign to plateau at roughly one third of
total coverage.

\subsection{Execution Speed Benchmark}
We measured \texttt{exec speed} under three configurations using the same
libpng 1.2.56 target compiled with the CRC patch applied (see
\hyperref[fig:status_nosanit]{Figure \ref*{fig:status_nosanit}} for config~(1),
\hyperref[fig:status_whitebox]{Figure \ref*{fig:status_whitebox}} for config~(2),
and \hyperref[fig:status_persistent]{Figure \ref*{fig:status_persistent}} for
config~(3)):

\begin{table}[h]
\centering
\small
\begin{tabular}{lr}
\toprule
Configuration & Exec Speed (exec/s) \\
\midrule
(1) No sanitizer + fork mode  &  6,607 \\
(2) ASan + fork mode          &    830 \\
(3) ASan + persistent mode    & 44,400 \\
\bottomrule
\end{tabular}
\caption{Execution speed across three instrumentation configurations.}
\label{tab:execspeed}
\end{table}

\textbf{No sanitizer + fork (6,607 exec/s):} Without ASan, there is no shadow
memory to initialize or maintain, and no redzone checks on every allocation and
access. The process still pays the \texttt{fork()} cost per test case, which
caps throughput.

\textbf{ASan + fork (830 exec/s):} Adding ASan reduces throughput by roughly
\textbf{8$\times$}. ASan maps one shadow byte for every 8 bytes of application
memory and inserts inline checks before every memory access. For libpng, which
performs many small heap allocations per image (row buffers, info structs, zlib
state), this overhead accumulates significantly per execution.

\textbf{ASan + persistent mode (44,400 exec/s):} Persistent mode eliminates the
\texttt{fork()} cost entirely by looping inside a single process using the
\texttt{\_\_AFL\_LOOP()} macro. The fuzzer delivers test cases via shared memory,
yielding a \textbf{53$\times$ speedup} over ASan + fork. ASan remains active but
its initialization cost is amortized over 10,000 iterations before the process
restarts.
